<decisions>
## Implementation Decisions

### Базлайн: список запросов (AUDIT-04)
- **D-01:** В стартовую таблицу базлайна берём ВСЕ коммерческие запросы из групп 1–3
  файла `seo/keywords.md` (~17–18 запросов): широкие коммерческие (группа 1), по услугам
  (группа 2), иногородние/сегмент C (группа 3). Группа 4 (информационные) в базлайн НЕ
  входит — она под будущий блог (Phase 14).
- **D-02:** Позиции фиксируем и в Яндексе, и в Google по каждому запросу. Список
  замораживается на старте фазы и далее не меняется — иначе не с чем будет сравнивать рост.

### Фильтрация собственного трафика (AUDIT-02)
- **D-03:** Свой трафик Марии исключаем через встроенную функцию Яндекс.Метрики
  «не учитывать мои визиты» (браузерная cookie-метка). Мария заходит на сайт и с
  компьютера, и с телефона — поэтому метку нужно проставить на КАЖДОМ устройстве (в
  браузере компьютера и в браузере телефона). План должен дать пошаговую инструкцию «куда
  нажать» для обоих устройств.
- **D-04:** Фильтр по IP-адресу НЕ используем: Мария заходит в том числе с мобильного, где
  IP динамический и постоянно меняется — фильтр по IP не сработает и даст ложное чувство
  чистоты. Встроенная метка Метрики надёжнее для этого сценария.

### Объём исправлений (AUDIT-05)
- **D-05:** В Phase 9 чиним ошибки ранга «критично» И «важно». Мелочь ранга «желательно»
  не чиним в этой фазе — заносим в чек-лист аудита как бэклог для будущих фаз. То есть
  Success Criterion 5 роадмапа (устранить критичное) расширяется: критичное + важное.

### Claude's Discretion
- **Доступы к кабинетам (AUDIT-02, AUDIT-03):** Мария решила этот вопрос не обсуждать.
  Рабочее допущение: у Марии есть рабочие логины к Яндекс.Метрике, Яндекс.Вебмастеру и
  Google Search Console. Все шаги, требующие входа в кабинет, оформляются в плане как
  пошаговые инструкции «куда кликнуть, что ввести, что должно появиться» (Мария —
  не программист). Если доступа к какому-то кабинету не окажется — это всплывёт на
  соответствующем шаге, тогда разберёмся отдельно.
- Технический инструментарий аудита (чем краулить сайт, как снимать Core Web Vitals,
  как собирать позиции) — на усмотрение Claude, в рамках бесплатных/разовых инструментов
  (Screaming Frog ≤500 URL, Lighthouse/PageSpeed, кабинеты Вебмастера/GSC).
- Формат и место хранения чек-листа аудита и таблицы базлайна — на усмотрение Claude
  (роадмап предполагает `.planning/audit/`).

</decisions>

## Existing Code Insights

### Reusable Assets
- `MetrikaCounter.astro` + `business.ts` (counterId 99532899): счётчик уже вставлен через
  единый компонент — проверить, что он подключается ровно один раз (нет дубля счётчиков) и

- `@astrojs/sitemap` в `astro.config.mjs`: sitemap генерируется автоматически при build —
  проверить содержимое `dist/sitemap-index.xml` на кириллицу/Punycode и полноту URL.
- `public/robots.txt`, `public/google...html`: robots и верификация Google уже на месте —
  аудит проверяет корректность, а не создаёт заново.

### Established Patterns
- Домен двойной: кириллица `крылья.life` (canonical, для людей) + Punycode
  `xn--j1aco8bgs.life` (техслой: robots Host/Sitemap, TLS). Критично: canonical и `<loc>`
  в sitemap — в кириллице; дублей кириллица/Punycode в GSC быть не должно (AUDIT-03).
- Хостинг Cloudflare Pages, автодеплой из GitHub main. Исправления критичных/важных ошибок
  кода деплоятся через обычный git push.

### Integration Points
- Кабинеты (внешние, ручные шаги Марии): Яндекс.Метрика, Яндекс.Вебмастер, Google Search

- Код сайта (`src/`, `public/`, `astro.config.mjs`) — здесь исправления on-page/технических
  ошибок ранга критично+важно.

## Specific Ideas

- Базлайн — это замороженная точка отсчёта. Таблица: запрос → позиция в Яндексе → позиция
  в Google → (показы/клики за 30 дней из Вебмастера/GSC) + отдельные строки: число
  проиндексированных страниц в Я.Вебмастере и в GSC. После фиксации список запросов не меняем.
- Инструкции для кабинетов — языком не-программиста: «открой …, нажми …, должно появиться …».

</specifics>
