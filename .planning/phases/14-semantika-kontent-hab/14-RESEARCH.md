## Summary

Технологическая часть фазы низкорискованная: репозиторий уже имеет отработанный паттерн Content Collections (`services`, `cases`, `testimonials`, `team`) с Zod-схемами через `astro:content`, и Phase 09-01 уже решила главную IDN-проблему — кириллический canonical через строковую конкатенацию вместо `new URL()`. Коллекция `ideas` добавляется тем же способом, что и `cases`: `glob`-loader на `**/*.md`, без MDX и без новых зависимостей для контента. Единственная новая npm-зависимость — `@astrojs/rss` (для `/rss.xml`), и её код был прочитан напрямую: библиотека **тоже использует `new URL()` внутри** и без обхода даст Punycode в `<link>` RSS-канала — это задокументированная находка с конкретным обходным путём (см. «Common Pitfalls» и «Code Examples»).

Семантическая часть требует ручной, но простой работы в бесплатном Yandex Wordstat (подтверждено веб-поиском: бесплатен, нужен только вход через Яндекс ID). Главная находка этого исследования — **прямой риск каннибализации у самой флагманской статьи** (D-03, заблокирована и не пересматривается): её тема почти дословно пересекается с замороженным базлайн-запросом №12 «организовать мероприятие в калининграде из москвы» (группа 3, сегмент C, коммерческий). Тема менять нельзя, но подачу (заголовок, H1, meta, перелинковку) необходимо развести с коммерческим интентом — конкретная рекомендация дана в «Common Pitfalls».

Третья находка — сайт использует **не автогенерируемый**, а вручную поддерживаемый `sitemap.xml.ts` (массив маршрутов как TS-литерал, без `@astrojs/sitemap`). Это значит: каждая новая статья `/идеи/` должна вручную добавляться в этот массив — иначе не попадёт в sitemap, при этом ARCHITECTURE.md (написан до Phase 09) ошибочно предполагает автогенерацию через `@astrojs/sitemap`.

**Primary recommendation:** Строить коллекцию `ideas` по образцу `cases` (plain Markdown, Zod-схема, `reference()` на `services`), завести отдельный `IdeaLayout.astro` (в отличие от cases/services, где отдельного layout-компонента нет — это оправдано требованием D-08 «каждая статья одинаково заканчивается мостиком»), использовать `@astrojs/rss` с абсолютными кириллическими URL в каждом `item.link` (обходит баг Punycode), и включать каждую новую статью вручную в `sitemap.xml.ts`. Семантику собирать в бесплатном Wordstat по кластерам из таблицы ниже, все информационные кластеры прогонять через сверку с `BASELINE.md` перед тем как отдавать их статье.

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Markdown (`**/*.md`, встроенный loader) | MDX (`**/*.mdx` + `@astrojs/mdx`) | ARCHITECTURE.md (написан 2026-06-26, до реализации `cases`/`services`) предполагал MDX. Но ни одна существующая коллекция сайта не использует MDX — все статьи и услуги на plain Markdown. MDX нужен только если в тело статьи потребуется встраивать Astro/React-компоненты (например, интерактивную галерею внутри текста). Для D-08 (мостик на услугу в конце статьи) это решается в `IdeaLayout` вне тела Markdown — MDX не требуется. **Рекомендация: Markdown, ноль новых зависимостей.** Если в процессе написания статей понадобятся встроенные компоненты — добавить `@astrojs/mdx` точечно, это обратно совместимое расширение (можно смешивать `.md` и `.mdx` в одной коллекции) |
| `@astrojs/rss` | Ручной XML-эндпоинт (как `sitemap.xml.ts`) | `sitemap.xml.ts` написан вручную, потому что `@astrojs/sitemap` **не мог** быть донастроен под кириллицу без глубокого форка. Для RSS другая ситуация: баг `@astrojs/rss` (Punycode в `<link>`) **обходится без форка библиотеки** — см. Code Examples. Ручная реализация RSS 2.0 с нуля (валидные RFC822-даты, экранирование HTML в `<description>`, `CDATA`) — больше кода и больше риска багов, чем обходной путь вокруг одной известной проблемы готовой библиотеки |
| `reference("services")` (одна услуга на статью) | `z.array(reference("services"))` (несколько услуг) | D-08 требует «мостик на **релевантную** услугу» (единственное число) — одна связь проще для авторского процесса (Claude предлагает 1 услугу при черновике, Мария не выбирает из списка). Массив избыточен для этой фазы |

**Почему `src/content/ideas/` остаётся ASCII, а кириллична только `src/pages/идеи/`:** минимизирует площадь риска Unicode-нормализации (см. Содержимое `src/content/` в HTML/URL не участвует напрямую, поэтому может (и должно) оставаться в ASCII.

### Pattern 1: Коллекция `ideas` — Zod-схема

**What:** Схема для frontmatter статей, зеркалящая конвенции `cases`/`services` (`z.coerce.date()`, `z.string()` для cover вместо `image()`-хелпера — на сайте нигде не используется `astro:assets`, обычные `<img>` + `public/assets/...`).

**When to use:** При добавлении коллекции в `src/content.config.ts`.

**Example:**
```typescript
// src/content.config.ts — добавить рядом с существующими
import { defineCollection, reference, z } from "astro:content";
```

### Pattern 2: `IdeaLayout.astro` как единственный layout-компонент

### Anti-Patterns to Avoid

- **Полагаться на `Astro.url.pathname` по умолчанию в `<Seo>` для страниц `/идеи/`:** `Astro.url` — это WHATWG `URL`-объект; его `.pathname` для кириллического сегмента `/идеи/...` вернёт **percent-encoded** строку (`/%D0%B8%D0%B4%D0%B5%D0%B8/...`), а не читаемую кириллицу. Всегда передавать `pathname` явным литералом (`` `/идеи/${d.slug}/` ``), как уже делает весь существующий код (`services/[slug].astro`, `cases/[slug].astro`) — там `pathname` **всегда** передан явно, ни разу не оставлен на дефолт.
- **Полагаться на `@astrojs/rss` без обхода Punycode-бага** — см. Common Pitfalls.
- **Класть JSON-LD `author` как `Person` («Мария Вострикова»)** — ARCHITECTURE.md (написан до утверждения D-02) предлагал именно это. Но D-02 фиксирует голос статей как **агентство «мы»**, не личный голос Марии. Правильнее — `author: { "@type": "Organization", "@id": ".../#organization" }`, ссылающийся на уже существующий `Organization`-узел из `JsonLdGraph.astro`, либо `Person` с ролью автора-редактора, если Мария решит подписывать статьи лично (тогда это отдельное решение, не входящее в текущий локап D-02).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| RSS 2.0 фид | Ручной XML-шаблон с `String.raw`/шаблонными строками | `@astrojs/rss` | Правильные RFC822-даты, экранирование `&`/`<`/`>` в `<title>`/`<description>`, валидная XML-структура — 3 строчки кода вместо десятков; единственное, что нужно обойти вручную — Punycode-баг (см. ниже), это не повод переписывать всю библиотеку |
| Кластеризация запросов | Автоматический NLP-кластеризатор / n-грамм скрипт | Ручная кластеризация по интенту в Wordstat + таблица в `seo/keywords.md` | При ~13 кластерах и ≈50-70 запросах ручная кластеризация занимает часы, а не дни; автоматизация оправдана от нескольких сотен ключей — здесь это оверинжиниринг под бюджет ≈0 ₽ (согласуется с PITFALLS.md Pitfall #9) |
| Хлебные крошки + микроразметка | Новый компонент для статей | Существующий `Breadcrumbs.astro` | Уже содержит ОБА формата разметки, требуемых D-11 (JSON-LD BreadcrumbList И itemscope/itemprop) — используется как есть, без изменений, просто с новым набором `crumbs` |

**Key insight:** Единственная реальная инженерная задача фазы — не создание нового, а точное повторение уже отработанных в репозитории паттернов (`cases` → `ideas`) с одним отличием (отдельный `IdeaLayout`) и одним обходом известного бага стороннего пакета.

## Common Pitfalls

### Pitfall 1: Флагманская статья почти дословно совпадает с замороженным коммерческим базлайн-запросом

**What goes wrong:** D-03 (заблокировано, не пересматривается) — тема «Как организовать корпоратив в Калининграде, если вы в другом городе». Базлайн-запрос №12 (`BASELINE.md`, группа 3, сегмент C, коммерческий, заморожен 03.07.2026): «организовать мероприятие в калининграде из москвы». Совпадение смысла почти полное (разница — «корпоратив» vs «мероприятие», «если вы в другом городе» vs «из москвы»). Если статья и будущая коммерческая посадка (главная, блок «Почему иногородним» на PAGE-01) начнут конкурировать за одну и ту же выдачу — оба URL «замигают» в позициях (см. PITFALLS.md Pitfall #2), а сравнение базлайна станет недостоверным.

**Why it happens:** Тема выбрана Марией из содержательных, не из SEO-соображений (она «самая практичная … снимает ключевое возражение» — CONTEXT.md D-03) — это правильный выбор для конверсии читателя, но он structurally близок к коммерческому интенту.

**How to avoid:** Тему **не менять** (locked decision). Развести подачу:
- Заголовок/H1/meta title статьи — обязательно с явным «как»-фреймингом («Как организовать…», «Пошаговый гид», «Что учесть, если вы...») — не голый инфинитив/номинатив («Организация мероприятия в Калининграде из Москвы»), который читается как коммерческий лендинг.
- В теле статьи — нет цен, нет CTA вида «закажите», «оставьте заявку» (кроме финального мостика D-08, который и так нейтральный).
- Перелинковка **односторонняя в сторону коммерции**: с главной (блок «Почему иногородним») и с `/services/corporate-parties/` можно поставить контекстную ссылку НА статью («Подробный разбор — как мы организуем корпоратив удалённо»), но сама статья ссылается на услугу мягким мостиком, не пытаясь встать вместо главной страницы в выдаче.
- После публикации — при следующем замере базлайна (не раньше, чем через месяц, per Pitfall #10 из PITFALLS.md) явно сверить, не поменялись ли позиции по запросу №12 у главной страницы — если появилась ротация, canonical-подсказка через `rel=canonical` на статью не поможет (разные страницы, разные темы), решение — усилить заголовок статьи ещё дальше от коммерческой формулировки.

**Warning signs:** GSC/Я.Вебмастер показывают ОБА URL (главная и статья) по запросу «организовать мероприятие в калининграде из москвы» одновременно в топ-20; позиция главной страницы по этому запросу падает в период публикации статьи.

**Phase to address:** Phase 14, до и сразу после публикации первой статьи. Проверка — часть плана HUB-05.

### Pitfall 2: `@astrojs/rss` использует `new URL()` внутри — Punycode в RSS-фиде

**What goes wrong:** Прочитан исходный код `@astrojs/rss` (`packages/astro-rss/src/util.ts`, актуальная ветка main на 2026-07-04) [VERIFIED: чтение исходников на GitHub]:
```typescript
export function createCanonicalURL(url, trailingSlash, base) {
  // ...
  const canonicalUrl = new URL(pathname, base).href; // ← нормализует IDN-хост в Punycode
  // ...
}
```
Канальная ссылка (`<link>` верхнего уровня RSS-фида) **всегда** проходит через эту функцию — `createCanonicalURL(site, trailingSlash, undefined)` — значит, она **всегда** выйдет в форме `https://xn--j1aco8bgs.life/`, даже если `astro.config.mjs` → `site` задан в кириллице. Это прямое повторение бага, который Phase 09-01 уже чинила в `Seo.astro`/`Breadcrumbs.astro`, но в стороннем пакете, форкать который не нужно.

**Why it happens:** Библиотека написана до появления кириллических IDN-кейсов в практике авторов пакета; WHATWG `URL`-парсер по спецификации всегда нормализует host в Punycode при парсинге абсолютного URL, независимо от того, передан `base` или нет.

**How to avoid:**
- Для **ссылок на статьи** (`item.link`) — обход существует и не требует форка: функция `isValidURL()` в библиотеке сначала проверяет `result.link` через `new URL(url)` (просто тест на парсируемость, возвращает `true`/`false`, **не** переприсваивает нормализованную форму), и если тест прошёл — **оригинальная строка используется без изменений**. Значит: если передать в `item.link` уже собранный **абсолютный** URL в кириллице (`business.urlCyrillic + "/идеи/" + slug + "/"`), а не относительный путь (`/идеи/${slug}/`), то `isValidURL` вернёт `true`, и итоговая ссылка в фиде останется кириллической.
- Для **канальной ссылки** (`site` → верхний `<link>` в `<channel>`) обхода нет — она безусловно проходит через `createCanonicalURL`, и итог будет в Punycode. Это единственное известное расхождение с D-11 «canonical всех статей в кириллице» — но касается не canonical статей (они генерируются в `Seo.astro`, уже верно), а служебной ссылки самого RSS-канала. Задокументировать как принятое ограничение стороннего пакета, не блокер.

**Warning signs:** `grep -c "xn--" dist/rss.xml` даёт больше 1 совпадения (норма — ровно одно, в канальном `<link>`); если совпадений много — обход `item.link` не сработал (скорее всего, передан относительный путь вместо абсолютного).

**Phase to address:** Phase 14, при реализации `src/pages/rss.xml.ts`. Верификация — тем же grep-паттерном, что и в Phase 09-01 (`grep -c "xn--" dist/...`).

### Pitfall 3: Кириллическая папка `src/pages/идеи/` — риск Unicode-нормализации macOS (NFD) vs Linux CI (NFC)

**What goes wrong:** Репозиторий разрабатывается на macOS (APFS), а сборка Cloudflare Pages выполняется на Linux-раннере. APFS хранит имена файлов в форме, зависящей от того, как файл создан (Finder создаёт в NFD, `zsh`/большинство CLI-инструментов — в NFC); Linux-файловые системы и git-объекты ожидают NFC. Если папка `идеи` будет создана в macOS Finder (а не через терминал/редактор), а `git config core.precomposeunicode` не включён, есть риск, что закоммиченное имя папки физически (побайтово) не совпадает между локальной копией и тем, что видит Linux-раннер — что теоретически может привести к неожиданному поведению при клонировании/пересборке (дублирующиеся записи каталога, файл «не найден» при точном сравнении путей). [MEDIUM confidence — риск подтверждён независимыми источниками про APFS/git, но конкретно для этого репозитория не воспроизведён]

**Why it happens:** APFS не нормализует имена файлов на уровне файловой системы (в отличие от старого HFS+, который принудительно нормализовал в NFD); macOS и Linux расходятся в конвенции по умолчанию.

**How to avoid:**
- Создавать папку `src/pages/идеи/` и файлы внутри неё **через инструмент/терминал** (`mkdir`, `Write`/`Edit` tool), не через Finder/drag-and-drop — так имя будет создано в предсказуемой форме (обычно NFC при создании через `zsh`/Node).
- Проверить `git config --get core.precomposeunicode` — если `true` (частая настройка на macOS с современным git), git сам приводит имена к NFC при коммите независимо от формы на диске.
- **Практическая верификация** (важнее теории): после первого деплоя сделать `curl -sI https://крылья.life/идеи/` (или через Punycode-форму) и убедиться, что страница отдаётся `200`, а не `404` — если Cloudflare Pages билд на Linux не нашёл файл из-за нормализации, это проявится немедленно и однозначно.

**Warning signs:** Локально (`npm run dev`) `/идеи/` работает, но после деплоя на Cloudflare Pages — 404 на все страницы раздела при том, что сборка (build log) прошла без ошибок.

**Phase to address:** Phase 14, сразу после первого деплоя раздела — добавить в план явный шаг «curl-проверка живого `/идеи/` после деплоя», по аналогии с уже принятым в проекте паттерном пост-деплой верификации (Phase 09-03).

### Pitfall 4: `sitemap.xml.ts` — вручную поддерживаемый список, не автогенерация

**What goes wrong:** ARCHITECTURE.md (написан 2026-06-26, до Phase 09) утверждает: «`@astrojs/sitemap` автоматически подхватывает все страницы, включая `/идеи/<slug>/`». Это **больше не так**: Phase 09-01 полностью удалила `@astrojs/sitemap` из `astro.config.mjs` (комментарий в коде: «плагин не поддерживает кириллические `<loc>` для IDN-доменов») и заменила его вручную поддерживаемым TS-массивом `routes` в `src/pages/sitemap.xml.ts` (сейчас содержит 20 строк, никак не связан с `getCollection()`). Если про это забыть — новые статьи `/идеи/` физически будут существовать на сайте (доступны по прямой ссылке, проиндексируются краулером через внутренние ссылки), но не появятся в sitemap → медленнее обнаруживаются, не участвуют в приоритизации через Я.Вебмастер «Переобход страниц».

**Why it happens:** Расхождение между ранним архитектурным исследованием (до фикса Phase 09) и текущим состоянием кода; естественная ловушка при чтении только `ARCHITECTURE.md` без сверки с актуальным `src/pages/sitemap.xml.ts`.

**How to avoid:** Каждую новую статью — вручную добавлять строкой в массив `routes` в `sitemap.xml.ts` (`"/идеи/<slug>/"`), либо (лучшее решение для этой фазы) переписать `routes` так, чтобы секция статей строилась через `getCollection("ideas")` динамически, а остальные маршруты (услуги, кейсы, статичные страницы) остались как явный список — гибрид «явный список + один динамический блок для ideas» снижает риск забыть добавление вручную при HUB-05 (публикация 2-3 статей — уже риск разъехаться).

**Warning signs:** `grep -c "идеи" dist/sitemap.xml` меньше числа опубликованных статей.

**Phase to address:** Phase 14, каждый task публикации статьи должен включать шаг обновления `sitemap.xml.ts` в Definition of Done.

### Pitfall 5: Каннибализация между статьями рубрики «Форматы» и услугами

**What goes wrong:** D-04 предлагает кандидата «Где провести корпоратив: площадки/форты/побережье» — это прямое пересечение с базлайн-запросом №16 «площадки для корпоратива калининград» (группа 3, коммерческий, заморожен). Сейчас на сайте нет отдельной коммерческой страницы-лендинга «площадки» (`PAGE-01..16` её не содержит) — то есть прямого конфликта с существующей страницей услуг нет, но конкурентный анализ (`competitor-world.md`, ось 3) прямо рекомендует Крыльям в будущем сделать посадочные страницы «формат + локация». Если такая страница появится позже, а статья блога уже заняла эту нишу с тем же заголовком — снова каннибализация, но теперь между будущей коммерческой страницой и уже проиндексированной статьёй.

**How to avoid:** Формулировать заголовок статьи через явный gid-формат («7 площадок Калининграда для корпоратива: от форта до побережья» — листинг, обзор) вместо голого совпадения с фразой «площадки для корпоратива калининград». Внутри статьи — мостик на `/services/corporate-parties/`, а не на гипотетическую будущую страницу «площадки» (её ещё нет). Зафиксировать как открытый вопрос для будущих фаз: если появится лендинг под «формат + локация», потребуется either редирект статьи на него, либо явное разведение интентов (лендинг = «заказать», статья = «выбрать/сравнить»).

**Phase to address:** Phase 14 — при написании этой статьи (если попадёт в первую волну плана HUB-04) или позже, если оставлена «на потом» согласно D-04.

### Бесплатный Wordstat-процесс (HUB-01)

1. **Вход:** `wordstat.yandex.ru`, авторизация через Яндекс ID Марии (сервис полностью бесплатен, требует только логин) [CITED: множественные независимые источники 2026 — adlook.me, practicum.yandex.ru, sostav.ru; проверено веб-поиском 2026-07-04].

4. Группировать **по общему интенту, не по общим словам** (подтверждено в PITFALLS.md со ссылкой на seohead.pro, MEDIUM confidence): один кластер = один тип контента, который закрывает весь набор запросов.

6. **Обязательная сверка каждого информационного кластера с 16 запросами `BASELINE.md`** — если пересечение слов >70% и нет модификатора «как/что/почему/список/гид» — переквалифицировать в коммерческий и НЕ отдавать статье (см. Pitfall 1 и 5 — конкретные найденные пересечения).

## Code Examples

### RSS-лента с обходом Punycode-бага

```typescript
// src/pages/rss.xml.ts
import rss from "@astrojs/rss";
import { getCollection } from "astro:content";
import { business } from "../config/business.ts";

export async function GET() {
  const ideas = (await getCollection("ideas", ({ data }) => !data.draft)).sort(
    (a, b) => b.data.publishDate.getTime() - a.data.publishDate.getTime()
  );

  const base = business.urlCyrillic.replace(/\/$/, "");

  return rss({
    title: "Идеи — Крылья",
    description: "Практические гайды и наблюдения об организации мероприятий в Калининграде",
    site: business.urlCyrillic, // канальный <link> всё равно уйдёт в Punycode — известное ограничение @astrojs/rss, см. Pitfall 2
    items: ideas.map((post) => ({
      title: post.data.title,
      pubDate: post.data.publishDate,
      description: post.data.description,
      // КРИТИЧНО: абсолютный кириллический URL, НЕ относительный путь —
      // isValidURL() внутри @astrojs/rss пропускает уже валидные абсолютные URL без нормализации в Punycode
      link: `${base}/идеи/${post.data.slug}/`,
    })),
  });
}
```

## Open Questions

1. **Нужен ли `@astrojs/mdx` в этой фазе?**
   - What we know: ни одна существующая коллекция не использует MDX; статьи по D-08 могут обойтись plain Markdown + логикой в `IdeaLayout`.
   - What's unclear: захочет ли Мария при редактуре встраивать что-то интерактивное прямо в текст статьи (галерея, кастомная врезка).
   - Recommendation: не устанавливать `@astrojs/mdx` в этой фазе; добавить точечно позже, если возникнет конкретная потребность — не блокирует HUB-03.

2. **Должна ли будущая посадочная страница «площадки Калининграда» существовать отдельно от статьи блога?**
   - What we know: `competitor-world.md` рекомендует лендинги «формат + локация»; `formats.md`/`REQUIREMENTS.md` пока не включают такую страницу в v2.0-скоуп.
   - What's unclear: попадёт ли эта тема в первую волну статей (D-04 оставляет решение Claude) и как её развести с гипотетическим будущим лендингом.
   - Recommendation: если кластер «Как выбрать площадку» попадает в план HUB-04 — использовать листинг-фрейминг заголовка (см. Pitfall 5) и явно пометить в самом плане тем как «на пересмотр, если появится лендинг «площадки»».

3. **Кто физически подписывается как `author` в JSON-LD BlogPosting?**
   - What we know: голос текста — агентство «мы» (D-02); ARCHITECTURE.md (устаревший черновик) предлагал `Person: Мария Вострикова`.
   - What's unclear: хочет ли Мария личное авторство в разметке (может помогать E-E-A-T сигналам Google) при том, что текст написан от «мы».
   - Recommendation: по умолчанию — `Organization` (соответствует голосу текста); если Мария предпочитает `Person` для E-E-A-T — это её решение, стоит явно спросить на discuss/plan-check, а не решать implicitly в коде.
